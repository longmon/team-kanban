## 1. Overview

An agent on your machine (Claude Code, Codex, or any MCP client) publishes generated pages — polls, forms, surveys, reports, knowledge pages, flowcharts, architecture diagrams — to a remote Team Kanban server. Organization members, or external users holding a temporary link, open them in a browser, fill them in and submit. The agent fetches the submissions over MCP; the web UI also shows results live and exports CSV.

```
local agent ──stdio──> tkanban mcp (Rust, mcp/) ──HTTPS + PAT──> Team Kanban server (Rust + PostgreSQL) <──browser── members / external users
```

- **Multi-tenant**: organization → project → page; org members, project roles (admin / editor / viewer), groups, invite links.
- **Two page kinds**: **OpenUI** (the agent writes OpenUI Lang, rendered by the official components; recommended) and **html** (self-contained HTML in a sandboxed iframe on a separate origin).
- **Page types (`page_type`)**:
  - Read-only — `report`, `knowledge` (auto table of contents), `flowchart`, `architecture` (rendered with Mermaid). No submissions; the agent does not wait for replies.
  - Collecting — `vote` (polls / forms / surveys). The agent waits with `get_responses`.
  - The agent picks a type that fits the request and uses yours if you name one. Older pages are `general` and behave as before.
- **Visibility**: `public` / `org` / `project` / `groups`. For outsiders, create temporary links with an expiry, a usage cap and an optional password.
- **Model attribution**: the publishing agent reports its model name (required by the MCP `publish_page` tool), and the page shows "由 {model} 生成" (generated by {model}). Pages published without it show nothing.
- **Agent access** uses personal access tokens (PAT) with scopes `publish` and `read_responses`.

### 2.3 From publish to response

1. The agent calls `get_ui_guide` (the MCP fetches and caches `/openui/prompt.md` and `/openui/library.schema.json` from the server) and writes OpenUI Lang.
2. `publish_page`: `tkanban mcp` validates the page locally with embedded QuickJS against the same schema, then calls `POST /api/pages` with the PAT and returns the page URL. For people outside the organization, it then calls `create_share_link`.
3. A user opens the page. OpenUI pages are rendered by kanbanLibrary; html pages run in a sandboxed iframe on `PAGES_ORIGIN` and submit through the host page via postMessage. Submissions are written to PostgreSQL and wake any waiters through the in-process notifier.
4. Read-only pages (report / knowledge / flowchart / architecture) end here — the agent just hands you the link. For collecting pages (votes / forms), the agent long-polls `GET /api/pages/{id}/responses` via `get_responses` (with `since` and `wait_seconds`; the server holds the request for up to 25 s) and returns as soon as something new arrives. The web results page refreshes live over SSE and can export CSV.

### 2.5 Security

- **Two-origin isolation**: html pages live on a separate host name, `PAGES_ORIGIN`. Requests are strictly routed by Host — the pages host serves only `/h/*`, the main host never serves `/h/*`. The iframe sandbox has no `allow-same-origin`, and `frame_url` is signed and expires.
- **CSP**: main-site responses send `default-src 'self'; script-src 'self'; font-src 'self' data:; frame-ancestors 'none'` and more. Fonts are self-hosted; external CDNs cannot be used (see [design-system.md](docs/design-system.md)).
- **Authentication**: the web UI uses a session cookie plus Origin/CSRF checks; agents use PATs (scopes `publish` / `read_responses`, optionally restricted to one org or project); external users use temporary links (expiry, usage cap, optional password).
- **Multi-tenancy**: org → project → page, project roles admin / editor / viewer, group grants; every permission check goes through `authz.rs`.
- **Single instance**: rate limiting and long-poll wake-ups are in-process — do not scale out horizontally.

More detail: [docs/design.md](docs/design.md) (architecture, data model, permission matrix), [docs/api.md](docs/api.md) (API contract, MCP tools), [docs/design-system.md](docs/design-system.md) (visual spec).

## 3. Usage

Everything on your machine is one binary, `tkanban` (`mcp/`, a single Rust file with no Node or OpenSSL dependency). It is both a CLI that manages multiple servers and the stdio MCP server (`tkanban mcp`).

> The binary inside the server Docker image is called `relay` (historical name, kept for compatibility) and runs on the server. `tkanban` runs on your own computer. They are unrelated.

### 3.1 Install tkanban

**Prebuilt binaries** — download from [GitHub Releases](https://github.com/longmon/team-kanban/releases), extract, and put `tkanban` on your `PATH`:

| Platform | Target |
|---|---|
| Linux x86_64 (static, any distro) | `x86_64-unknown-linux-musl` |
| Linux arm64 (static, any distro) | `aarch64-unknown-linux-musl` |
| macOS Apple Silicon | `aarch64-apple-darwin` |
| macOS Intel | `x86_64-apple-darwin` |
| Windows x86_64 | `x86_64-pc-windows-msvc` (`.zip`) |

Assets are named `tkanban-<tag>-<target>.tar.gz` (`.zip` on Windows), with `SHA256SUMS.txt` alongside. For example:

```bash
curl -L https://github.com/longmon/team-kanban/releases/latest/download/tkanban-v2.1.0-x86_64-unknown-linux-musl.tar.gz | tar xz
# macOS, if the first run is blocked:
xattr -d com.apple.quarantine tkanban
```

**From source** (needs Rust 1.89+ and a C compiler; installs to `~/.cargo/bin/tkanban`):

```bash
cargo install --git https://github.com/longmon/team-kanban team-kanban
# or, inside a clone of this repo:
cd mcp && cargo build --release && sudo install -m 0755 target/release/tkanban /usr/local/bin/tkanban
```

Run `tkanban --help` for the built-in help (in Chinese).

### 3.2 Connect to a server

First create a token in the web UI: **Tokens** page (`/settings/tokens`; labelled 令牌 in the UI). Publishing needs scope `publish`, reading submissions needs `read_responses`; a token can be restricted to one org or project. The token is shown only once.

```bash
# Add a server (profile). The token is verified online and the orgs / projects / groups it can publish to are listed;
# nothing is saved if verification fails. Without --token you are prompted (no echo), keeping it out of shell history.
tkanban add depx --url https://dash.tkanban.com --default

# Token from stdin, plus default publish targets for this server (treated as "specified by the user")
printf '%s\n' "$ANOTHER_PAT" | tkanban add another --url https://relay.example.com \
  --org acme --project demo --group design --group ops

tkanban test                       # check connectivity and tokens
```

A default server only applies if you set one explicitly (`--default` above, or `tkanban default <name>`).

### 3.3 Register with an MCP client

No `TEAM_KANBAN_URL` / `TEAM_KANBAN_TOKEN` needed — servers come from the config file.

**Claude Code** (`-s user` makes it global):

```bash
claude mcp add team-kanban -s user -- "$(command -v tkanban)" mcp
```

**Codex** — either run:

```bash
codex mcp add team-kanban -- tkanban mcp
```

or edit `~/.codex/config.toml`:

```toml
[mcp_servers.team-kanban]
command = "tkanban"          # or an absolute path such as /usr/local/bin/tkanban
args = ["mcp"]
tool_timeout_sec = 60        # get_responses long-polls for up to 25 s; leave headroom
```

**Any other MCP client**: register a stdio server whose command is `tkanban` (absolute path recommended) with argument `mcp`. Running `tkanban` with no subcommand also starts the MCP server. Allow a tool timeout above 25 s.

### 3.4 Config file

`$XDG_CONFIG_HOME/team-kanban/config.toml` (default `~/.config/team-kanban/config.toml`), file mode 0600, directory 0700. `tkanban add/remove/default` maintain it; you can also edit it by hand. If the old path `agent-relay/config.toml` (historical name) exists and the new one does not, it is migrated automatically on first run.

```toml
default = "depx"

[profiles.depx]
url = "https://dash.tkanban.com"
token = "arp_xxxx…"          # "arp_" token prefix is a historical name

[profiles.another]
url = "https://relay.example.com"
token = "arp_yyyy…"
org = "acme"
project = "demo"
groups = ["design", "ops"]
```

Legacy mode: if the MCP process has `TEAM_KANBAN_URL` (+ `TEAM_KANBAN_TOKEN`) in its environment, that becomes a server named `env` and competes with the configured ones. After switching to the config file, remove `-e TEAM_KANBAN_URL… -e TEAM_KANBAN_TOKEN…` from your registration, or you will get an extra `env` candidate. HTTP requests honour the standard `HTTPS_PROXY` / `NO_PROXY` variables.

### 3.5 MCP tools

| Tool | Purpose |
|---|---|
| `get_ui_guide` | How to write OpenUI (call it first): server prompt + validated examples + html fallback notes |
| `list_targets` | Servers and the orgs / projects / groups you can publish to on each |
| `list_projects` | Projects you belong to |
| `publish_page` | Publish a page. `page_type` and `model` (the agent's own model name, e.g. `Claude Opus 5.5`) are required; `kind=openui` is validated locally before upload |
| `update_page` | Update a page's content; optional `model` overwrites the recorded model |
| `create_share_link` | Temporary link for people outside the org |
| `get_responses` | Fetch submissions; supports `wait_seconds` long polling; for `vote` (and legacy `general`) pages |
| `list_pages` | List pages |

Typical flow: `get_ui_guide` → `list_targets` (if needed) → `publish_page` → `create_share_link` if outsiders need to view or fill it in → for `vote` pages, loop `get_responses` with `server`, `since` and `wait_seconds`; read-only pages need no waiting. The page shows "Generated by {model}".

Full contract: [mcp/README.md](mcp/README.md) and [docs/api.md](docs/api.md) §14.

### 3.6 Target selection rules

The agent follows these rules:

- Resolve server → org → project in order. Whatever you named in the conversation wins; `org` / `project` / `groups` configured on a profile count as named.
- If not named: a level with a single candidate is used directly; with several, the tool returns "selection needed" with candidates (name / slug / id) and the agent asks you which server, project or group to use.
- The default server applies only after `tkanban add --default` or `tkanban default <name>`. With several servers and no default, you are asked every time.
- If groups are given, the page goes to those groups (visibility `groups`). Without groups you are not asked, and visibility defaults to `project`. If a group name exists in several orgs, you are asked to choose.
- Publish results include `server`; reading submissions, updating the page and creating share links afterwards all pass it along.

### 3.7 What to say in chat

- "Publish this weekly report to the acme/weekly project on depx."
- "Make a poll and send it to the 'design' group on the another server."
- "Send it to the design and ops groups on depx, and create a 7-day temporary link for an external colleague."
- "Where can I publish?" (the agent calls `list_targets` to list servers, projects and groups)
- "Draw the deployment as an architecture diagram." / "Turn this guide into a knowledge page." (read-only; you get a link, no waiting)
- If you don't say where and there are several choices, the agent lists candidates first, e.g. "depx or another?"

### 3.8 CLI reference

| Command | Description |
|---|---|
| `tkanban add <name> --url <URL> [--token <PAT>] [--org <slug>] [--project <slug>] [--group <name>]... [--default]` | Add a server; verifies the token online and lists publish targets. Without `--token` (or `--token -`) it prompts in a terminal or reads the first line of stdin |
| `tkanban list` | List servers and the default (tokens masked, `*` marks the default) |
| `tkanban remove <name>` | Remove a server |
| `tkanban default <name>` / `tkanban default --clear` | Set / clear the default server |
| `tkanban targets [name]` | List publishable orgs, projects, groups live (all servers by default) |
| `tkanban test [name]` | Test connectivity and token (all servers by default) |
| `tkanban mcp` | Start the stdio MCP server (also the behaviour with no subcommand) |
| `tkanban --help` / `--version` | Help / version |

## 4. Deployment / Self-hosting

### 4.1 Quick local trial (Docker)

Starts only `pg` and `app` (no Caddy) — needs nothing but Docker with the compose plugin:

```bash
git clone https://github.com/longmon/team-kanban.git && cd team-kanban
cat > .env <<EOF
SECRET_KEY=$(openssl rand -hex 32)
PG_PASSWORD=$(openssl rand -hex 16)
PUBLIC_URL=http://127.0.0.1:8080
PAGES_ORIGIN=http://localhost:8080
COOKIE_SECURE=0
TRUST_PROXY=0
PUBLIC_HOST=localhost   # only to pass compose validation; caddy is not started locally
PAGES_HOST=localhost
EOF
chmod 600 .env
docker compose up -d --build pg app
```

Open <http://127.0.0.1:8080>, register, create an org and a project, then create a PAT on the Tokens page and continue with [3.2](#32-connect-to-a-server) using `--url http://127.0.0.1:8080`.

- `127.0.0.1` and `localhost` are two different origins, so they stand in for the main site and the html-pages origin. Always browse via `PUBLIC_URL` exactly.
- `COOKIE_SECURE=0` because over plain http browsers refuse `Secure` / `__Host-` cookies — login would not stick.
- `PUBLIC_HOST` / `PAGES_HOST` are required by `docker-compose.yml` (for the caddy service) even when caddy isn't started.

Common commands:

```bash
docker compose logs -f app          # logs
docker compose down                 # stop (data stays in the pgdata volume; add -v to wipe it)
git pull && docker compose up -d --build pg app   # update
```

### 4.2 Using an external PostgreSQL

Build the image and run it against your own database:

```bash
docker build -f server/Dockerfile -t team-kanban .     # build context is the repo root (BuildKit required)

cat > team-kanban.env <<EOF
DATABASE_URL=postgres://USER:PASSWORD@host.docker.internal:5432/teamkanban
SECRET_KEY=$(openssl rand -hex 32)
PUBLIC_URL=http://127.0.0.1:8080
PAGES_ORIGIN=http://localhost:8080
COOKIE_SECURE=0
EOF
chmod 600 team-kanban.env

docker run -d --name team-kanban --restart unless-stopped \
  --env-file team-kanban.env -p 127.0.0.1:8080:8080 \
  --add-host=host.docker.internal:host-gateway \
  team-kanban
```

`host.docker.internal` reaches PostgreSQL on the Docker host; on Linux it requires `--add-host=host.docker.internal:host-gateway` (Docker Desktop has it built in). For production behind a reverse proxy, use https URLs, `COOKIE_SECURE=1` (default) and `TRUST_PROXY=1` — see [4.5](#45-environment-variables).

Requirements and caveats:

- **Version**: PostgreSQL 13+ recommended (production runs 17). No extensions needed.
- **Privileges**: migrations run automatically at startup, so the account needs to create and alter tables in that database.
- **No TLS to the database**: the server is built without sqlx TLS support (`server/Cargo.toml` enables no `tls-*` feature), so managed databases that enforce `sslmode=require` cannot be reached. Don't connect to a database across the public internet.
- **No PgBouncer in transaction mode**: migrations take a session-level advisory lock.
- **Keep `SECRET_KEY` fixed**: store it once (as in the env file above), don't regenerate it on every run. Changing it invalidates the signed grants of share-link visitors (they must reopen the link) and outstanding html `frame_url`s.
- **Single instance only**: notifications are in-process (`server/src/notify.rs`); run one container per database.

### 4.3 Develop from source

Requires Rust 1.89+, Node 22, and Docker (only for PostgreSQL).

```bash
# 1) Database (container name agent-relay-pg and DB name relay_dev are historical names kept for compatibility)
docker run -d --name agent-relay-pg -e POSTGRES_PASSWORD=dev -p 127.0.0.1:55432:5432 postgres:17-alpine
docker exec agent-relay-pg psql -U postgres -c "CREATE DATABASE relay_dev"

# 2) Frontend (web/dist is embedded into the backend binary)
cd web && OPENUI_TELEMETRY_DISABLED=1 npm ci && npm run build && cd ..

# 3) Backend (runs migrations at startup)
cd server && cargo build --release
DATABASE_URL=postgres://postgres:dev@127.0.0.1:55432/relay_dev \
PUBLIC_URL=http://127.0.0.1:8080 \
PAGES_ORIGIN=http://localhost:8080 \
SECRET_KEY=$(openssl rand -hex 32) \
COOKIE_SECURE=0 \
./target/release/relay
```

Open <http://127.0.0.1:8080>, register → create an org → create a project → create a PAT on the Tokens page. As in 4.1, `127.0.0.1` and `localhost` simulate the two origins.

**Frontend work** with Vite hot reload: keep the backend on 8080, run `cd web && npm run dev` and open <http://localhost:5173>. `/api`, `/openui` and `/h` are proxied to 8080 (override with `TEAM_KANBAN_DEV_TARGET`).

### 4.4 Production deployment

`docker compose` runs three services:

- `pg` — `postgres:17-alpine`, named volume `pgdata`, not exposed.
- `app` — bound to `127.0.0.1:8080` only; defaults `TRUST_PROXY=1`, `COOKIE_SECURE=1`.
- `caddy` — host network, listens on 80/443, configured by `Caddyfile`. Host networking is used because ports published by Docker bypass firewalld.

`Caddyfile` assumes Cloudflare proxying (orange cloud): it trusts only the Cloudflare ranges in `cf-trusted.caddy`, takes the client IP from `CF-Connecting-IP`, and passes it to the app as the sole `X-Forwarded-For`. Certificates come from Let's Encrypt via HTTP-01; set Cloudflare SSL/TLS to Full (strict). Without Cloudflare, delete the three lines inside the `servers` block.

#### 4.4.1 First deployment: prepare the server

1. Install Docker with the compose plugin and confirm `docker compose version` works; `scripts/cf-firewall.sh` needs firewalld and curl. The deploy directory is fixed at `/opt/agent-relay` (historical name, kept for compatibility); work as root.
2. Point two host names at the server (Cloudflare proxied), e.g. `kanban.example.com` (main site) and `pages.example.com` (html pages origin — **not** a sub-path of the main site).
3. Write `/opt/agent-relay/.env` on the server (compose reads it automatically; replace every value with your own):

   ```bash
   mkdir -p /opt/agent-relay && cd /opt/agent-relay
   cat > .env <<EOF
   PUBLIC_HOST=kanban.example.com
   PAGES_HOST=pages.example.com
   PUBLIC_URL=https://kanban.example.com
   PAGES_ORIGIN=https://pages.example.com
   SECRET_KEY=$(openssl rand -hex 32)
   PG_PASSWORD=$(openssl rand -hex 16)
   # Optional:
   # ALLOW_SIGNUP=0
   # SMTP_URL=smtps://user:pass@smtp.example.com:465
   # SMTP_FROM=Team Kanban <noreply@example.com>
   # RUST_LOG=info
   EOF
   chmod 600 .env
   ```

   - Compose requires `PUBLIC_HOST`, `PAGES_HOST` (Caddy site names) and `SECRET_KEY`. `PUBLIC_URL`, `PAGES_ORIGIN` and `PG_PASSWORD` fall back to `http://localhost:8080`, empty and `relay` respectively — always set them in production. Keep the compose defaults for `TRUST_PROXY` and `COOKIE_SECURE`. `PG_PASSWORD` only takes effect when the `pgdata` volume is first initialised; don't change it later.
   - **Changing domains**: list the old main host in `PUBLIC_HOST` too (space-separated, quoted) and set the new one as `PRIMARY_HOST`. Web pages on the old host 308-redirect to the new one, while `/api/*` and `/openui/*` keep working, so tkanban installs configured with the old URL are unaffected. Example: `PUBLIC_HOST="kanban.example.com old.example.com"`, `PRIMARY_HOST=kanban.example.com`.
4. Run `scripts/deploy.sh user@host` once from your machine (see 4.4.2). On the first run there is no `cf-trusted.caddy` on the server, so it runs `cf-firewall.sh`: the firewalld public zone allows only ssh, 80/443 are opened to Cloudflare ranges only, and `cf-trusted.caddy` is generated.
5. Cloudflare's ranges change; add a weekly cron on the server, e.g. `0 4 * * 1 /opt/agent-relay/cf-firewall.sh` (idempotent; hot-reloads caddy).
6. Open `https://kanban.example.com` and register the first account. To make sign-up invite-only afterwards, add `ALLOW_SIGNUP=0` to `.env` and deploy again.

Without deploy.sh you can also `git clone` the repo on the server, add `.env`, and run `sudo scripts/cf-firewall.sh && docker compose up -d --build`.

#### 4.4.2 Routine deploys: `scripts/deploy.sh user@host`

Run it in your local clone. The argument is an SSH target with key-based login that can manage docker and firewalld (usually root). Without an argument it reads `DEPLOY_HOST`; with neither it exits with an error.

```bash
git commit ...                 # only committed content is deployed
scripts/deploy.sh user@host
```

What it does:

1. Packs **committed** content with `git archive HEAD`; uncommitted changes only trigger a warning and are not included.
2. Streams it over ssh; on the server it runs `mkdir -p /opt/agent-relay`, **deletes the five directories `docs mcp scripts server web`** and then extracts, so renamed or deleted files don't linger. Server-local files outside those directories (`.env`, `cf-trusted.caddy`, `backups/`, …) are untouched; root files `docker-compose.yml`, `Caddyfile`, `README.md` are overwritten.
3. Runs `/opt/agent-relay/scripts/deploy.sh --remote` on the server, which:
   - symlinks `/opt/agent-relay/deploy.sh` and `/opt/agent-relay/cf-firewall.sh` to the scripts of the same name under `scripts/`;
   - runs `cf-firewall.sh` if `cf-trusted.caddy` is missing;
   - runs `docker compose up -d --build --remove-orphans` (builds web and server inside the image, recreates changed containers);
   - runs `docker image prune -f` and prints `docker compose ps`.

On the server you can also run `/opt/agent-relay/deploy.sh --remote` directly to rebuild from the code already there.

#### 4.4.3 Database migrations

No manual SQL. Migrations live in `server/migrations/`, are compiled into the binary by `sqlx::migrate!`, and run before the app starts listening. If a migration fails the process exits (log shows 迁移失败, "migration failed") and the container restarts in a loop. To change the schema, add a new migration file and deploy it with the code. Never edit a migration that has been released (e.g. `0001_init.sql`) — sqlx refuses to start on a checksum mismatch.

`0002_page_types.sql` (page types) and `0003_page_model.sql` (generating model) only add one column each (`page_type` with a constant default — old pages become `general`; nullable `generated_by`) plus CHECK constraints, without rewriting the table. Both set `lock_timeout = 5s`: if a long transaction holds the lock, the migration fails and is retried after the container restarts — deal with the long transaction first.

#### 4.4.4 Post-deploy checks

On the server:

```bash
cd /opt/agent-relay
docker compose ps                    # pg / app / caddy should all be healthy
docker compose logs --tail=100 app   # expect "listening on 0.0.0.0:8080" and no 迁移失败 (migration failed)
docker compose logs --tail=50 caddy  # were certificates issued?
curl --noproxy '*' -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/   # expect 200
```

There is no dedicated health endpoint; the compose health check simply requests `/`. `--noproxy '*'` is only for hitting the local address directly. From anywhere:

```bash
curl -fsS -o /dev/null -w '%{http_code}\n' https://kanban.example.com/              # expect 200
curl -fsS https://kanban.example.com/openui/library.schema.json | head -c 100; echo  # schema the MCP depends on
```

Then run `tkanban test` locally to confirm the PAT and connectivity.

#### 4.4.5 Rollback

There is no rollback script; redeploy an older commit:

```bash
git checkout <old-commit>
scripts/deploy.sh user@host
git checkout -                 # back to your branch
```

Migrations only go forward: if migrations were added after the version you roll back to, the old binary fails to start because the database contains migrations it doesn't know. Either fix the schema by hand first or roll forward with a fix. Rolling back to before 0002 requires stopping the app and running the rollback SQL in [design.md](docs/design.md) §3.3 (page types).

#### 4.4.6 Backups

The repo has no backup script or service; export manually when needed (into `/opt/agent-relay/backups/`, which deploy.sh never deletes):

```bash
cd /opt/agent-relay && mkdir -p backups
docker compose exec -T pg pg_dump -U postgres relay | gzip > backups/relay-$(date +%F).sql.gz   # DB name "relay" is a historical name
```

### 4.5 Environment variables

Read by the server (`server/src/config.rs`):

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | required | PostgreSQL connection string |
| `PUBLIC_URL` | required | Main site URL without trailing `/`; used to build links and check `Origin` |
| `PAGES_ORIGIN` | empty | Separate origin (another host name) for html pages. If empty, html pages share the main origin and rely on the sandbox alone — **required in production** |
| `SECRET_KEY` | required | Random string ≥ 32 bytes; signs `frame_url`s, share-link grants, etc. Keep it stable |
| `BIND` | `0.0.0.0:8080` | Listen address |
| `COOKIE_SECURE` | `1` | Set `0` for local http (the cookie name then changes from `__Host-relay_session` to `relay_session`; the cookie name is historical, kept for compatibility) |
| `TRUST_PROXY` | `0` | Set `1` behind a reverse proxy to take the client IP from `X-Forwarded-For` (for rate limiting) |
| `ALLOW_SIGNUP` | `1` | `0` = invite-only registration |
| `SMTP_URL` / `SMTP_FROM` | empty | Verification, invite and password-reset emails; if unset, email content is only logged |
| `RUST_LOG` | `info` | Log level |

Used only by `docker-compose.yml` / Caddy:

| Variable | Default | Description |
|---|---|---|
| `PUBLIC_HOST` | required | Caddy site name(s) for the main site; may list old hosts, space-separated |
| `PAGES_HOST` | required | Caddy site name for the html pages origin |
| `PRIMARY_HOST` | `PUBLIC_HOST` | The canonical main host when `PUBLIC_HOST` lists several |
| `PG_PASSWORD` | `relay` | Postgres password, applied only when the `pgdata` volume is first created |

Note: under compose, `app` defaults to `TRUST_PROXY=1`, unlike the binary's own default of `0`.

## 5. Testing

```bash
cd server && cargo test && cargo clippy --all-targets -- -D warnings   # needs the PG container from 4.3 (override with TEST_DATABASE_URL)
cd mcp && cargo test
cd web && npx tsc --noEmit && npm run check
scripts/e2e.sh                                                         # end-to-end, see below
```

`scripts/e2e.sh` creates a temporary database → builds web/server and starts it (finds a free port) → creates a user / org / project / PAT with curl → runs the MCP smoke test (`mcp/tests/live.rs`, which launches the real `tkanban` binary over stdio in env mode and calls every tool) → runs the browser e2e (`web/e2e/e2e.mjs`, playwright-core + a local headless chromium) → stops the server and drops the database.
Set the browser with `CHROME=`; by default it looks for `~/.cache/ms-playwright/chromium_headless_shell-*` (install with `npx playwright install chromium-headless-shell`).

## 7. FAQ

**Redirected back to login right after signing in / every write returns 403 `csrf_failed`**
Over plain http you must set `COOKIE_SECURE=0`, otherwise the browser won't store the `__Host-` cookie. Also `PUBLIC_URL` must match the browser's origin exactly (`127.0.0.1` and `localhost` are different origins) — the server checks `Origin`.

**html page is blank or reports frame-ancestors**
The `PAGES_ORIGIN` host serves only `/h/*`, and the main host doesn't serve `/h/*`. Check that the reverse proxy forwards the `Host` of `pages.example.com` unchanged. `frame_url` expires after 10 minutes and the frontend refreshes it automatically; updating page content invalidates old `frame_url`s immediately.

**MCP returns `openui_invalid:`**
The OpenUI is invalid and was rejected locally, not uploaded. Fix it using the returned `line:col code message` entries; call `get_ui_guide` for component signatures and examples.

**MCP returns `forbidden (HTTP 403)` / `not_found (HTTP 404)`**
The PAT lacks a scope (`publish` to publish, `read_responses` to read submissions), or its org/project restriction doesn't cover the target page. PATs cannot call web-session-only endpoints and cannot submit (`not_allowed`).

**External user sees "page does not exist, or you need to log in"**
The page's visibility isn't `public`. Create a temporary link with `create_share_link` for people outside the org instead of sending `/pages/{id}`.

**Registration returns 429**
At most 5 registrations per IP per hour (in-process limit, reset on restart); login 20 per minute; submissions 30 per IP per minute.

**CSV column names differ from the web table?**
They follow the same rule (api.md §8.4): OpenUI submissions have columns `action`, `form` and the form field names. If a field name collides with a fixed column (`seq`, `created_at`, …) or with `action`/`form`, it gets a `values.` prefix; for non-OpenUI submissions the prefix is `data.`.

**Can I run several app replicas?**
No. Rate limiting and long-poll wake-ups are in-process; run a single app instance (see design.md §9).
